# 喵测・评需求｜需求评审会，我是怎么揪出需求里的坑

大家好呀～上一期咱们聊了新项目到手第一天怎么摸底，今天接着往下走一步。

> 📌 **项目前提**（和上一期一样）  
> 全新从 0 搭起来的练习项目，基于 SimpleAdmin 框架开发，业务背景、用户、角色全部 AI 虚构，不是真实项目。

摸底那一步做完，接下来发生的第一件事就是：产品把 PRD 初稿发过来了。

很多新人到这儿的反应是： PRD 从头到尾看一遍，看懂了，然后开始等开发提测。

我一般不建议这么做。**看懂 PRD 和看出 PRD 的坑，是两件事。**

下面带你走一遍：评审会前我怎么准备、会上怎么问、问不出来的问题又该怎么办。

## 📦 本期项目速览

| 项目     | 内容                              |
| ------ | ------------------------------- |
| 项目名    | SimpleHR（简人系统）                  |
| 用户规模   | 虚构公司简好科技，约 200 人                |
| 四条业务主线 | 考勤打卡 · 请假 · 审批流 · 报销            |
| 本期重点   | 打卡规则判定、审批流状态机、报销财务合规            |
| 我的活儿   | 啃 PRD → 攒问题清单 → 拉评审会 → 把坑全部问出结论 |

业务主线理出来长这样，评审前我心里得有这张图：

```
员工每天打卡
   │
   ├── 缺卡 ──► 发起补卡申请 ──┐
   ├── 有事 ──► 发起请假申请 ──┤
   ├── 加班 ──► 发起加班申请 ──┼──► 通用审批流 ──► 通过/驳回/撤回
   │                           │         │
   │                           │         └──► 报销单 ──► 待打款 ──► 已打款
   └───────────────────────────┘
```

> 一眼能看出来：**审批流是四条线共用的引擎**，这块就是深水区，会上重点抠它。

## 一、先说好哦：需求评审不是去听产品念文档

先把这件事说清楚——需求评审会上，测试不是听众。

> ❌ **最低配的评审会**  
> 产品念一遍 PRD → 开发估工时 → 测试在旁边点头 → 散会

> ✅ **测试该干的事**  
> 把「还没写进 PRD 的场景」提前问出来，并且当场拿到结论

原因很实在：需求里漏掉的一条规则，开发按自己的理解写完，提测之后你才发现。这时候要么当成 bug 来回扯，要么走需求变更重做代码。

**同样一个问题，评审会上问清楚的成本是五分钟，提测后发现的成本是三天。**

## 二、会前：PRD 我一般读两遍

|    | 第一遍：通读          | 第二遍：找茬    |
| -- | --------------- | --------- |
| 目的 | 看懂业务在干什么        | 找出没写清楚的地方 |
| 关注 | 给谁用、主线怎么流转、哪块最难 | 边界、异常、并发  |
| 产出 | 一张业务主线图         | 一份编号问题清单  |

第二遍我一般带着三个万能提问逐条抠：

| 🔍 三问           | 它帮我挖出来的东西                     |
| --------------- | ----------------------------- |
| **边界在哪？**       | 恰好 1 天、恰好 1000 元、第 90 天，走哪条规则 |
| **异常怎么办？**      | 缺卡、跨天、跨月、审批人离职，系统怎么处理         |
| **两个人同时操作会怎样？** | 并发审批、重复提交这类 PRD 里默认不会发生的事     |

经验是：需求的坑八成不在正常流程里，全藏在「刚好卡在边界上」的场景。我当时抠出来的这些👇

| 编号 | 我抠出来的问题                                        | 类型         |
| -- | ---------------------------------------------- | ---------- |
| 01 | 固定班 09:00 上班，**09:00:01** 打卡算不算迟到？             | ⏱ 时间边界     |
| 02 | 一天取最早和最晚两次打卡，中午出去吃饭**多打两次**呢？                  | 🔁 重复数据    |
| 03 | 「缺卡走补卡」——**缺卡和旷工**怎么区分？                        | ⚠️ 概念歧义    |
| 04 | 夜班 22:00 → 次日 06:00 跨天，这条考勤算哪天的？**31 号夜班跨月**呢？ | 📅 跨天跨月    |
| 05 | 分级审批「≤1 天一级」，**恰好请 1 天**走哪级？报销恰好 1000 元呢？      | 💰 金额/时长边界 |
| 06 | 「审批人缺席自动跳过」——**审批人就是申请人自己**呢？                  | 👤 自审冲突    |
| 07 | 两个人同时打开同一张单子，都点「通过」？                           | ⚡ 并发       |
| 08 | 发票号全局唯一，**被驳回的单子还占号吗**？                        | 🧾 状态与事实   |

💡 **小技巧**：自己抠完这一版，再把 PRD 丢给 AI 让它也挑一遍刺，两边对一下，经常能补出我没想到的角度（上一期也提过，AI 就是拿来干这个的）。

会前我一共攒了二十多条。**别空手去开会**——带着编号的问题清单进场，产品想含糊都难。

## 三、会上：提问要带场景，别问开放题

第一轮评审，会议室里坐着产品小陈、前端阿伟、后端老周和我。我给自己定了条规矩：

> 📏 **我的会上规矩**  
> 每个问题都要当场拿到一个**能写进 PRD 的结论**，拿不到就记「待确认」，绝不让它稀里糊涂混过去。

这里有个很关键的提问方式——**别问开放式问题**。

| ❌ 开放式问法                      | ✅ 场景式问法                             |
| ---------------------------- | ----------------------------------- |
| 「迟到规则写清楚了吗？」  
→ 产品一定回你「写了呀」 | 「09:00:01 打卡算不算迟到？」  
→ 他必须给你一个是或不是 |
| 「报销金额有上限吧？」                  | 「单笔 20000，那恰好 20000 元能不能提交？」        |

几个印象最深的回合，记下来是这样的：

| 🙋 我问                     | ✅ 当场结论                       | 后面用在哪         |
| ------------------------- | ---------------------------- | ------------- |
| 恰好请 1 天走哪级？恰好报 1000 元走哪级？ | **含头不含尾**：1 天走一级、1000 元走两级   | 直接变成一整排边界值用例  |
| 部门管理员给自己报销，自己批自己？         | 该级**自动跳过**升级下一级，记录标注「自动跳过」   | 审批链异常场景       |
| 两人同时打开同一张单子都点通过？          | **先提交者生效**，后提交提示「该单据已被处理」    | 并发用例（这类最容易漏测） |
| 发票号被驳回的单子还占号吗？            | 进过审批的单**驳回也占号**，草稿不占         | 防重复报销用例       |
| 月累计额度含「审批中」，被驳回后释放吗？      | **释放**，额度按已打款 + 已通过 + 审批中实时算 | 额度扣减与回补       |
| 金额两位小数，20 行汇总会有分位误差吗？     | 后端**按分（整数）存储计算**，杜绝浮点误差      | 金额精度专项        |

## 四、答不上来的问题，别硬问产品，拉业务方进来

第一轮闭环了一批，但剩下几个谁都答不上来👇

| ⏳ 遗留问题     | 为什么答不上来                 |
| ---------- | ----------------------- |
| 年假余额怎么核定   | 规则在 HR 手上，产品只有一句「按入职年份」 |
| 销假按什么折算返还  | 涉及余额回补，HR 才有口径          |
| 病假材料什么时候补交 | 属于 HR 执行流程，不是系统逻辑       |

这类问题的共同点是：**不是产品拍脑袋能定的，得问真正干活的人。**

所以第二轮我提了个要求：**把 HR 代表刘姐请来列席。**

> 💬 **刘姐一开口，全是细节**  
> 「3 月攒的调休也只放到次年 4 月 30 号过期。」  
> 「31 号提交、次月才批的病假，月度报表得做修正，不能记成旷工。」  
> 「旷工不能自动触发扣款，得我们人工确认。」

这些要是没问出来，全是我提测之后才会炸的雷。

## 五、评审完别忘了收口

| 📊 项   | 结果                             |
| ------ | ------------------------------ |
| 两轮问题总数 | **36 个**                       |
| 当场闭环   | ✅ **32 个**（结论写进 PRD 条款）        |
| 进二期    | 🔁 **4 个**（外勤打卡次数管控、审批超时自动升级等） |
| PRD 版本 | 初稿 → **V2.0 定稿**，开发进排期         |

我最看重的收口动作是：**每个闭环的问题都标上结论落在 PRD 哪一条**（比如「含头不含尾」→ FD-APR-04）。

这样开发照着结论写代码，我后面写用例也照着同一份结论写，两边不会跑偏。

## 六、给测试小白的小提醒 🐱

- [x] 会前一定带着**编号的问题清单**去，别指望现场发挥
- [x] 提问带具体场景：**「09:00:01 算不算迟到」**&#x6C38;远比「规则清楚吗」好使
- [x] 边界问题**当场逼结论**：含头不含尾、第 7 天能不能补卡、第 90 天能不能报销
- [x] 业务规则找**真正的业务方**，产品和开发替 HR、替财务做不了主
- [x] 评审结论要**落到 PRD 条款上**，只口头说过等于没结论
- [x] 别怕问得多，评审会上多花一小时，比提测后来回扯三天值多了
